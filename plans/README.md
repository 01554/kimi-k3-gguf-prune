## Selection robustness — source-level split-half (Kimi-K3 builds)

How stable is the expert selection against changes in the calibration mix?
We split the calibration **by source domain** and compare the keep-sets each
half would produce. Note this is deliberately **harsher than a random
split-half** (as e.g. pipenetwork's reap75 card reports): random halves
share a distribution; domain halves are a distribution shift. The numbers
below therefore bound domain sensitivity, not sampling noise.

Overlap = mean fraction of the keep-set shared by both halves.
Oracle retention = how much of half B's saliency mass half A's selection
captures, relative to B's own optimal selection (both directions shown).

**REAP640 (keep-640, en+code calibration: web-en / code-multi / code-python):**

| split | keep overlap | oracle retention (A on B / B on A) |
|---|---:|---:|
| code-multi vs rest | 78.2% | 83.9% / 89.9% |
| code-python vs rest | 78.5% | 86.1% / 82.5% |
| web-en vs code | 74.2% | 66.0% / 76.0% |

**REAP576 (keep-576):** same pattern, slightly lower (overlap 66.8–72.4%,
retention 59.0–85.7%) — tighter budgets amplify domain sensitivity.

**REAP640ja (keep-640, lang-ja vs chinese):** overlap 83.8%, retention
89.0% / 91.1%.

Reading: selection is robust between related domains (code↔code ≈ 84–90%
retention; ja↔zh ≈ 90%) and visibly domain-sensitive across the
language↔code divide (66% retention) — consistent with our depth-resolved
expert-overlap analysis. This is why the calibration mix is disclosed on
every card: **the corpus is part of the model.**

Qwen builds: counts were archived only in aggregate, so a retroactive
split is not possible; a two-halves recalibration run is queued and will be
added here when measured.
